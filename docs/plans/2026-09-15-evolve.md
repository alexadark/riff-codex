# RIFF evolve implementation plan

Status: planned, implementation deferred until the current start/discovery work is complete and verified.

## Outcome

Add `$riff:evolve` for an existing RIFF application. It challenges a requested product change, checks its consequences against the real application, and prepares the necessary roadmap changes. It stops at a verified planning handoff; `$riff:wave` implements the result.

Support both a single feature request and a set of related requests from a collaborator or meeting. A collaborator's suggestion is input to evaluate, not automatically an approved product commitment. Respect the user's actual request: exploration may end with a recommendation and no roadmap mutation; an authorized planning request produces the revised plan.

This document authorizes no implementation, consumer changes, publication, or deployment. It records the agreed future work.

## Agreed entry paths

1. Existing RIFF project: `$riff:evolve`, then `$riff:wave`.
2. Application without RIFF: install RIFF, `$riff:map`, `$riff:onboard`, `$riff:evolve`, then `$riff:wave`.

Keep those steps explicit. Evolve checks prerequisites and points to the missing step; it does not silently install RIFF, run onboarding, or manufacture project context. Map describes the existing system. Onboard establishes the RIFF baseline and reuses the map rather than repeating discovery. The baseline describes existing capabilities without inventing retrospective delivery phases.

## Product behavior

### 1. Establish the current baseline

Read project instructions, `PROJECT.md`, `ROADMAP.yaml`, relevant specs and taste, a reusable map when available, and current CLI status. Inspect actual code and verification evidence around the requested change. Distinguish documented intent, implemented behavior, verified behavior, and assumptions.

Reuse map findings after checking the affected areas for drift. A saved map is useful context, not proof that the current application still matches it. Reconcile relevant discrepancies explicitly without initiating an unrelated repository audit.

### 2. Challenge the request

Identify the user, present problem, desired observable outcome, smallest useful scope, exclusions, and reasons for the change. For multiple requests, identify conflicts and shared outcomes before splitting work.

Explain consequential alternatives in ordinary language. Infer technical facts from the repository rather than interviewing the user about them. Follow configured autonomy: loop makes conservative decisions and records assumptions; guided asks only unresolved questions that materially change the product boundary. An explicit request for a product discussion allows that discussion without introducing a mandatory approval ceremony for every evolution.

### 3. Analyze consequences

Produce a focused current-to-target explanation covering the affected journeys, screens and states, data and migrations, permissions and tenancy, integrations, and operational behavior. Identify what existing users must retain and what must change. Include migration, recovery, and rollout constraints only where the actual change warrants them.

Connect each material impact to evidence or a clearly marked assumption. Reuse existing approved design and decisions. Do not turn a feature request into an unsolicited redesign, refactor, or system replacement.

### 4. Revise the plan

Present a concise change summary: added phases, revised future phases, replaced or deferred work, changed dependencies, and unaffected commitments that matter to the change.

- Preserve completed phase IDs, historical outcomes, and receipts. A change to delivered behavior gets new work.
- Revise pending phases only where affected, preserving roadmap representation, comments, key order, and unknown fields.
- Use only supported lifecycle semantics for replaced or deferred phases. Inspect the final CLI model before choosing an encoding; do not invent a status the scheduler ignores.
- Never silently rewrite the target of an active phase. Detect active work, record the conflict, and keep dependent planning non-activatable until the supported safe handoff or pause is established. Do not interrupt another task automatically.
- Use stable story and criterion IDs and real dependencies. Each phase delivers a demonstrable outcome with a justified P0-P3 priority, explicit exclusions, and relevant regression criteria.
- If the request is already covered, explain the existing coverage instead of adding duplicate phases.

`PROJECT.md` and `ROADMAP.yaml` remain authoritative. Store supporting evolution analysis in the project's existing specification structure, linked from the product synthesis, without creating a second backlog or copying the entire dossier.

### 5. Verify planning readiness and stop

Update only affected specifications, diagrams, story mappings, and readiness references. For enrolled projects, reuse the final discovery snapshot/review/check lifecycle so a changed dossier cannot reuse stale approval evidence. Preserve historical delivery evidence while requiring fresh readiness evidence for the changed plan.

For legacy onboarded projects, explicitly follow the final supported enrollment policy. Do not require a complete unrelated application dossier for every bounded feature or silently bypass readiness for a material evolution.

Synchronize derived state through the RIFF CLI only. Report the planned outcome, key assumptions, phase changes, verification result, and the next `$riff:wave` invocation when ready. Evolve itself never activates a wave.

## Implementation sequence

### A. Reconcile with completed start

Confirm the completed start contract, roadmap lifecycle capabilities, readiness behavior, and skill exposure mechanism. Resolve integration details from that implementation. Keep the agreed user-facing flow above.

Deliverable: a concrete file-level change scope with no duplicate discovery mechanism.

### B. Implement evolve and its shared contract

Create `riff/skills/evolve/SKILL.md` and its required agent metadata, plus a focused evolution reference if needed. Reuse shared discovery sections instead of copying them. Register/expose the command through the existing installation mechanism.

Prefer instruction and reference changes when the CLI already supports the required behavior. Add minimal CLI support only for a demonstrated gap, especially active-phase protection or roadmap replacement semantics.

### C. Align neighboring commands

Make map reuse explicit in onboard. Document the installed-but-not-onboarded prerequisite failure for evolve. Keep add-phase as the bounded one-phase operation; route requests requiring product reconsideration or multiple interacting phase changes toward evolve. Preserve start's role for initial product definition and wave's execution boundary.

Update command discovery and user documentation with both entry paths and one worked example: adding team invitations to an application with individual accounts. Show existing-user preservation, permissions, and observable new behavior without prescribing a universal implementation.

### D. Validate the feature

Use the smallest relevant existing checks, with at most five new or materially expanded automated scenarios unless a concrete risk justifies more:

1. An onboarded application receives a bounded evolution with an impact summary and demonstrable phases, while historical phases and unknown roadmap fields remain intact.
2. A non-onboarded application receives the explicit prerequisite path; a saved map is reused by onboarding without duplicate discovery or invented historical phases.
3. Multiple interacting requests revise future dependencies without duplicates; an already covered outcome creates no redundant phase.
4. Active work cannot be silently retargeted, and changed enrolled dossiers invalidate previous readiness evidence until a fresh passing check.
5. Evolve ends at planning readiness, does not activate implementation, and preserves the supported behavior for a legacy onboarded project.

Use fixture or CLI tests for actual lifecycle behavior and contract checks for registration. Separately review a worked planning example for product quality: presence of words in a skill is not proof that the plan challenges the need or protects existing users.

Run the affected existing tests and required RIFF validation. Review the final diff, commit only this feature's explicit changes locally, and report remaining external verification limits. Push and release require delivery authorization.

## Acceptance criteria

- Both product questioning and impact-aware replanning are represented in the command's outputs.
- The explicit install → map → onboard → evolve → wave path is documented and respected.
- Onboard reuses relevant map findings; evolve checks current evidence for drift.
- Completed history survives; pending changes are understandable; active work is protected.
- New behavior and affected existing behavior have observable acceptance criteria.
- Shared discovery/readiness logic is reused, with no parallel state or backlog.
- The command is discoverable through the normal RIFF installation path.
- Planning readiness is verified, and implementation remains a separate wave.

## Out of scope

Collaboration accounts, voting or approval systems, external issue synchronization, automatic installation/onboarding inside evolve, automatic wave execution, exhaustive unrelated audits, and deployment are outside this feature.
